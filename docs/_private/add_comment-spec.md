# 外部仕様書: docstring 追加

## 1. 目的
本仕様書は、`src/yklibpy` 配下の Python ソースコードに対して、クラス定義、メソッド定義、関数定義の先頭へ日本語の docstring を追加または再記述するための要求事項を定義する。

本作業の目的は、各定義の責務、前提条件、返値、失敗条件を読み取りやすくし、実装意図をコード上で一貫して参照できるようにすることである。

## 2. 背景
要求元は `_private/20260313/add_comment-req.md` である。

本リポジトリは Python 3.14 を前提とし、型ヒントおよび静的解析を活用する方針を取っている。したがって、docstring は型情報の重複説明ではなく、利用者と実装者の双方にとって有用な意味情報を補うものでなければならない。

## 3. 対象範囲
対象は `src/yklibpy` 配下の `.py` ファイルとする。

対象となる記述は以下のとおりとする。

- モジュールレベル関数
- クラス定義
- クラスのインスタンスメソッド
- クラスメソッド
- スタティックメソッド
- 特殊メソッド `__init__`
- 既存コードに存在する公開・非公開メソッド

以下も対象に含む。

- 既存 docstring が未記述の定義
- 既存 docstring があるが、本仕様の方針と整合しない定義
- 1 行要約のみで、前提・返値・失敗条件の補足が必要な定義

## 4. 非対象
本作業では、原則として以下を対象外とする。

- 関数、メソッド、クラスの振る舞い変更
- API 名称変更
- 型ヒントの新規追加や全面見直し
- docstring 追加だけを目的としない大規模リファクタリング
- ロジック整理、分割、統合などの構造変更
- 使用例の大量追記

ただし、docstring を自然に記述するために最小限の整形が必要な場合は、その修正を許容する。

## 5. docstring 記述方針
docstring は PEP 257 ベースの簡潔な日本語で記述する。

- 日本語で記述する
- クラス名、メソッド名、関数名、引数名は英語表記のまま用いる
- 基本は PEP 257 に沿った 1〜3 段落の簡潔な形式とする
- 引数や例外の説明が多い定義に限り、日本語の Google style を用いる
- 型の説明は型ヒントに委ね、docstring では意味、制約、前提を記述する
- 実装詳細の逐語的説明ではなく、利用時に必要な振る舞い上の情報を記述する

docstring では、型ヒントが存在することを前提として、少なくとも以下の観点を必要に応じて記述する。

- 何をするか
- どのような条件や前提で動作するか
- 何を返すか
- どのような場合に失敗するか

短く表現できる定義は、要約文と必要最小限の補足で完結させる。

引数、返値、例外の説明が複数あり、段落形式では読みづらい定義のみ、`Args`、`Returns`、`Raises` などの Google style セクションを用いてよい。

## 6. 既存 docstring の扱い
既存の docstring は、以下の方針で扱う。

- 既存 docstring がある場合は、いったん削除したうえで本仕様に従って再記述する
- 既存 docstring の言語、粒度、スタイルが混在している場合は統一する
- 型の説明が中心となっている記述は、意味や制約の説明へ置き換える
- 冗長な実装手順の説明や、コードから自明な説明は削減する
- 要求に対して十分である既存情報は、簡潔化したうえで再利用してよい

## 7. 記述粒度の基準
記述量は、定義の複雑さに応じて決める。

- 単純なアクセサや薄い委譲処理は、1 文または短い 1 段落でよい
- 条件分岐、状態変更、外部入出力、例外条件を持つ定義は、前提や失敗条件を補足する
- クラス定義には、その責務と保持する対象の概要を記述する
- `__init__` には、初期化対象、前提となる引数、初期化時の制約を記述してよい

## 8. 実装上の制約
docstring 追加にあたり、以下を満たすこと。

- 既存の公開 API の呼び出し方法を変更しない
- import 構成を不必要に変更しない
- docstring 追加のためだけに新しい外部依存を導入しない
- 型情報の重複説明を避ける
- 英語名を日本語へ置換しない
- クラス、関数、メソッドごとの記述スタイルを極端にばらつかせない

## 9. 受入条件
本仕様の完了条件は以下のとおりとする。

- `src/yklibpy` 配下の対象クラス定義、関数定義、メソッド定義の先頭に docstring が記述されている
- 既存 docstring は本仕様に従う形式へ再記述され、記述スタイルの混在が解消されている
- docstring は日本語で記述され、クラス名、関数名、メソッド名、引数名は英語表記のまま維持されている
- 短い定義は PEP 257 ベースの簡潔な形式で記述されている
- 複雑な定義のみ、日本語 Google style の `Args`、`Returns`、`Raises` などを用いて記述されている
- docstring が型ヒントの単純な繰り返しになっていない
- docstring 追加によって既存の動作や公開 API が不必要に変更されていない

## 10. 検証方法
検証は少なくとも以下の観点で行う。

- 対象モジュールを走査し、クラス、関数、メソッドの各定義に docstring が存在することを確認する
- 既存 docstring が残存していても、本仕様の記述方針に従う内容へ置換されていることを確認する
- docstring の記述が型情報の羅列ではなく、責務、前提、返値、失敗条件の説明になっていることを確認する
- `ruff check src` で新たな lint エラーを発生させないことを確認する
- `mypy src/yklibpy` の既存方針と矛盾する変更を導入していないことを確認する

## 11. 注意事項
本仕様の主目的は、すべての対象定義に対して、簡潔で一貫した日本語 docstring を付与することである。

定義ごとの複雑さに差があるため、すべてを一律に Google style で詳細記述することまでは要求しない。簡潔さを優先しつつ、利用時に不足する情報のみを補うことを原則とする。

また、既存コードに歴史的な表記ゆれや説明不足がある場合でも、docstring 追加を契機に全面的な設計見直しを行うことは要求しない。大きな設計判断が必要な箇所は、別要求として切り出す。

## 12. 想定される要注意領域
以下のようなモジュールでは、外部入出力、動的データ、OS 依存処理、設定値の受け渡しが多く、前提条件や失敗条件の説明が重要になる。

- `src/yklibpy/db/appstore.py`
- `src/yklibpy/db/storex.py`
- `src/yklibpy/common/util.py`
- `src/yklibpy/htmlparser/scraper.py`
- `src/yklibpy/tomlop/tomlop.py`

以上を、本要求に対する docstring 追加作業の外部仕様とする。
